# WTLS discovery queue

Use this queue to decide what to investigate through discovery, design review, and a clean-room implementation when a change is warranted. Queue entries are research questions. The [WAP-199 support boundary](WAP_199_PROVISIONED_TRUST_PLAN.md#support-boundary) and [evidence matrix](WAP_199_EVIDENCE_MATRIX.md) retain authority over scope and verified behavior. Source notes belong in the [KWTLS reference](KWTLS_SOURCE_REFERENCE.md).

The two starting controls are the BlackBerry 7290 against KWTLS on RSA/DES-CBC/full SHA and the same BlackBerry against the Rust gateway on RSA/3DES-CBC-EDE/full SHA. Record the roles and negotiated suite on every result. The Rust client still needs independent gateway evidence for the exact supported profile. ## Evidence for closing an item

Keep the spec section, named peer and build, roles, suite, observed packets and outcome with the finding. Choose a disposition at review. Options include retaining evidence, adding a focused test, correcting the implementation to match the spec, improving an adapter while preserving wire behavior, adding a peer-specific option, or deferring. Where the evidence only covers deterministic Rust behavior, record that level explicitly.

For a clean-room implementation round, hand off the agreed observable behavior, corrected spec, approved fixtures and acceptance tests in an isolated workspace. Keep historical source and discovery notes on the research side. Implementation starts after the behavior and tests are reviewed.
